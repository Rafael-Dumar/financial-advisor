The clarified stock trade-approval policy now explicitly requires verified timing so that the existing proximity rule cannot be bypassed. This is asset-specific and leaves primary grade and unrelated assets intact. `tests/test_hardening.py:88-110,124-140,560-580` check unknown/near/imminent event handling; `tests/test_analyst_review_semantics.py:835-858` confirms missing earnings does not itself block report grade. No inspected authoritative test or document establishes that an equity with unverified timing was intentionally allowed to remain `tradeable`. The current `no_upcoming_event_found` status can arise from an empty or past-only payload (`advisor/data_pipeline.py:64-109,176-191`); that status alone does not prove the risk window was checked and clear.

Current classifier rule inventory: base labels depend on swing/investment scores: `<45` swing or `<25` investment → `avoid`; `<60` swing → `wait`; `≥75` swing and `≥70` investment → `tradeable`; `≥70` swing with `<50` investment → `technical_unvalidated`; otherwise `watch_buy` (`advisor/scoring.py:1103-1197`). Explicit hard-gate alerts are `low_liquidity`, `event_risk`, `earnings_imminent`, `earnings_near`, `market_risk_off`, `market_not_risk_on`, `position_too_small_for_risk`, `recent_gap_risk`, and `small_market_cap`; imminent earnings chooses `wait` where that branch is reached (`advisor/scoring.py:520-575,898-917`). A measured below-configured-minimum market cap overrides to `avoid` (`advisor/scoring.py:880-901`). The conjunction of investment score `<45`, recent gap, invalid PE/PEG and win rate `<45%` imposes a technical cap (`advisor/scoring.py:1267-1324,794-815`). `high_volatility`, `possible_priced_in`, `news_risk_off`, `post_earnings_gap`, `recent_guidance`, and `liquidation_pressure` are current alerts/score inputs as described above, not independent members of the hard-gate set. Leverage eligibility is a separate policy: confidence `<65` or high/critical missing-data severity disables leverage, without independently changing the entry label (`advisor/risk.py:69-81`; `advisor/report.py:1549-1553`).

## 8. Confirmed bugs and inconsistencies

1. **False session warning** — `_telegram_reason` tests `"market_session_conflict" in diagnostic`, so a diagnostic line `market_session_conflict: false` triggers the conflict explanation and “main not used” text. `_main_decision_grade_diagnostic_lines` can generate that line even from a decision-grade summary; `_telegram_summary` calls the reason on no-trade. This is field-presence/substring matching instead of semantic boolean parsing (`advisor/analyst_review.py:1236-1296,1735-1765,2118-2127`). Another function, `_data_error_summary`, correctly checks `market_session_conflict: true` (`advisor/analyst_review.py:2145-2156`).
2. **False decision-grade wait** — `_objective_reading_lines` emits “esperar main decision-grade” unconditionally for non-tradeable final decisions, even when `main_not_decision_grade=False`. This is hardcoded generic guidance, not a derived blocker (`advisor/analyst_review.py:878-907`). Asset card text also contains generic main-grade guidance (`advisor/analyst_review.py:949-953,1697-1703`).
   The separate no-trade Telegram fallback says the main did not confirm a candidate “pelo gate de integridade” even when the main gate passed; its text is likewise not derived from the asset-level reason (`advisor/analyst_review.py:2118-2127`).
3. **Crypto regime absent-as-zero** — `_derive_crypto_regime` uses `funding_rate or 0.0` and `open_interest_change or 0.0`; `classify_crypto_regime` can then award `funding_balanced` for unobserved funding. This is a current semantic mismatch, not grounds for a universal flow hard requirement (`advisor/scan_engine.py:62-85`; `advisor/regime.py:79-88`).
4. **Generic optional-data caps** — flow, liquidations, premium, and selected fundamentals are high/medium severity because of their reason-code spelling; no equivalent explicit absence rule exists for every field. `mixed_provider_data` similarly caps on brand without proving incompatibility. See sections 2–5.
5. **Separate review grade can disagree** — `_report_data_grade` accepts `diagnostic_not_decision_grade` as compatible with decision-grade display if its other checks pass. Main operational gate remains separate, but the displayed grade may contradict primary authority (`advisor/analyst_review.py:981-1014,345-414`).
6. **Runtime audit inconsistency, root cause not proven for the cited runs** — report CLI writes a runtime trace under `reports/runtime` when `--runtime-scoring-artifact` is enabled; scheduled workflow enables it and uploads `reports/` (`advisor/cli.py:310-318,918-1004`; `.github/workflows/financial-advisor-reports.yml:92-110`). Fetch script selects main/close reports, downloads their artifacts to `run-<id>-<type>`, then passes those roots to `advisor.runtime_scoring_intake` and writes `reports/runtime/nightly-runtime-manifest.json` (`scripts/fetch-latest-github-reports.ps1:380-514`). Intake searches recursively for one allowlisted trace whose immediate parent is `runtime`; if absent it emits `runtime_missing` / `validation_status=not_found` (`advisor/runtime_scoring_intake.py:156-205,318-329`). Final review reads only the sanitized manifest and labels it `observability_only`; tests verify variants do not alter authority/Telegram (`advisor/analyst_review.py:144-220,505-548`; `tests/test_phase25_final_review.py:449-540`). The specific production roots, directory listings, producer trace status and manifest were not provided locally for the cited cycles. Therefore one cannot prove whether the trace was not produced, excluded from upload, or absent from the selected downloaded root. Valid report markdown alone does not prove runtime trace presence. No current decision effect is established.

## 9. Resolved policy decisions and planning boundary (second clarification pass)

The three financial-policy questions from the first pass are resolved below. “Available” means valid, traceable evidence for the consuming rule; an unverified label or mere field presence is insufficient. Current implementation effects remain in sections 2–8 and are not silently adopted as the approved policy.

Earnings status reconciliation: current `verified` is tied to a parsed upcoming date; current loader failures use `provider_unavailable` or `plan_restricted` (approved category: `source_unavailable` with precise cause); the snapshot default is `not_implemented`; a genuinely omitted collection is `not_collected`; `not_applicable` belongs only to a scope where the stock event gate does not apply. Current `no_upcoming_event_found` can result from an empty or past-only payload and must not be silently treated as verified clearance without a source-backed covered window (`advisor/data_pipeline.py:64-109,176-191`; `advisor/live_loader.py:716-739,1428-1430`; `advisor/models.py:75-99`). These are semantic categories, not a mandate for new collection or a new provider.

Mixed-provider incompatibility is concrete when evidence shows inconsistent asset or instrument identity; venue meaning changes; unnormalized currency or units; incompatible directly compared timeframes; intraday and EOD observations treated as timestamp-equivalent; freshness outside the rule's window; materially conflicting same-capability values without precedence/reconciliation; missing per-capability provenance; incompatible metric definitions; or a required capability assembled from sources that cannot safely be combined. Such a demonstrated problem may limit the affected rule or asset. The existing `source_mismatch_possible` and ADR `provider_market_cap_mismatch_possible` flags are **possibility warnings**, not demonstrations. Existing stale-price handling is a concrete freshness gate; existing price-basis and fetch metadata help establish provenance but do not alone prove that every provider combination is compatible (`advisor/scoring.py:1579-1588,1668-1818`; `advisor/models.py:47-75`; `advisor/data_sources.py:179-205`). The feature remains free-first and permits valid fallbacks; no single provider must supply every capability.

The current tests that expect `ev_components_missing` to reduce confidence and mark EV `limited/model_estimate`, and the test that expects a fallback price provider to reduce confidence, document the **old implementation** (`tests/test_hardening.py:193-226,750-785`). They are explicit future implementation mismatches with the clarified contract; they were not edited in this phase. An adequate-sample backtest with missing consumed rate/EV can also bypass the corresponding current comparison; this is a code-path mismatch, not a claim about the cited production assets. No inspected earnings test proves that unverified timing was intentionally allowed for a stock `tradeable` result. The current earnings-risk tests instead assert honest unknown status and an imminent-event wait (`tests/test_hardening.py:88-110,124-140,560-580`).

**Remaining financial-policy questions: none.** Runtime producer/upload/selected-root attribution remains a bounded observability investigation requiring the selected run artifact trees, producer status/logs, and intake manifest; it is not an operational blocker or a policy choice. Implementation design questions such as where to validate capability compatibility and how to carry the resulting trace belong to `/speckit.plan`. No decision above relaxes measured market, event, backtest, freshness, history, or sizing risk gates. The approved specification is normative; conflicting current behavior is `CURRENT_IMPLEMENTATION_MISMATCH`.
