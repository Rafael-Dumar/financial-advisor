## Summary and success boundary

Keep `advisor/scoring.py` and the existing report-grade evaluator as financial authorities. Replace the use of reason-code spelling as a universal eligibility rule with small, explicit rule/capability outcomes produced where the rule already executes. Carry those outcomes, provider provenance, and observed market facts through the existing report and final-review artifact path. The final review uses the main's authoritative `source_decision` plus its existing integrity gate, and renders explanations from the carried outcomes; it does not rescore assets. Real required gaps still fail closed at their own scope. Optional gaps remain visible without an artificial cap. No threshold, strategy, risk fraction, order path, or trade-frequency target changes.

Success is a traceable thesis-based, data-limited, or report-integrity-limited result, including a truthful `no_trade`. The implementation must demonstrate both required-data fail-closed behavior and optional-data nonblocking behavior, then be observed in at least two later **natural scheduled** production cycles. Neither cycles nor tests run in this planning phase.

## Technical context and constitution gate

- Runtime is Python; the report job calls `score_asset`/`classify_asset`, `render_markdown_report`, and `render_analyst_review_input` in `advisor/cli.py`. `scripts/fetch-latest-github-reports.ps1` selects and packages the generated main/close artifacts. `advisor/analyst_review.py` parses the selected raw main report and emits the final review and `## Telegram summary`.
- `AssetSnapshot` already carries candles, event status, quote/daily-change values, data-source and fetch metadata, benchmark provenance, and crypto metric provenance. `AssetDecision` already carries source decision, limitations, reason codes, quality/confidence, and backtest stats (`advisor/models.py`). Add only the minimal typed outcome fields needed for transport; avoid a second scoring object graph.
- `advisor/runtime_scoring_observability.py` has a frozen 97-rule catalog and optional runtime traces, but runtime intake can be absent. It is unsuitable as the sole nightly decision trace or a new operational authority. Reference existing stable rule IDs where applicable; emit a small always-present decision-effect ledger from the classification path, not a copy of the 97-rule runtime trace.
- `evaluate_report_grades` in `advisor/report.py` owns primary, overall, and discovery grades. Its primary conditions remain live mode, fresh primary data, regular conflict-free primary session, benchmark session when supplied, and regular window when enforced. `main_blocks_operation` in `advisor/analyst_review.py` owns the subsequent artifact/provenance/identity/blocking-reason gate.
- Existing reports are Markdown contracts. The raw main report is the selected decision source; analyst-review input and nightly input may carry a subset and references. A versioned, bounded, deterministic field/section can be added without changing artifact selection or workflow transport.
- No `.specify/memory/constitution.md`, local plan template, setup script, or `.specify/extensions.yml` exists in this checkout. Use the approved spec, evidence matrix, repository instructions, and this feature's no-code/no-workflow boundaries as the gate. No extension hook is registered. Post-design check: the design adds no provider, service, database, broker action, or financial threshold.

## Architecture and ownership

1. **Rule-scoped criticality**: keep the compact explicit dependency map beside the consuming branches in `advisor/scoring.py`, with any shared value type in `advisor/models.py`. Each applicable rule names its capability, scope, and criticality (`REQUIRED_FOR_DECISION`, `REQUIRED_FOR_SPECIFIC_RULE`, `OPTIONAL_CONTEXT`, `DIAGNOSTIC_ONLY`, `NOT_APPLICABLE`, `UNSUPPORTED`). A reason code is an explanation/compatibility label, never the authority for criticality. No global catalog of every possible feed and no new service.
2. **Evidence status**: normalize loader/pipeline facts at the snapshot-to-decision boundary, preserving raw provider status and per-capability provenance. Use `available`, `temporary_provider_failure`, `provider_restriction`, `not_collected`, `unsupported`, `not_implemented`, `not_applicable`, `invalid`, or `stale`. Status describes observation; criticality describes rule dependency. A valid authorized fallback satisfies the capability even while the failed provider remains recorded.
3. **Effect ledger**: each material rule records whether it was evaluated, passed, failed on observed financial evidence, or unresolved because required evidence was absent/invalid; its decision effect and existing reason code accompany the authoritative `AssetDecision`. Score and risk functions remain unchanged except where current generic missing-data effects contradict the approved contract. An effect entry must be produced at the branch that applies it, not inferred later from text.
4. **Report and review boundary**: `advisor/report.py` serializes the ledger in main asset sections and a normalized market-context section. `advisor/analyst_review.py` validates/parses the versioned fields and renders a compact human audit. Legacy fields (`decision_label`, `reason_codes`, alerts, limitations, grades) remain. The final review cannot promote an asset from old or incomplete trace data. See [contracts/decision-evidence.md](contracts/decision-evidence.md) and [data-model.md](data-model.md).

### Status × criticality decision table

| Criticality at applicable scope | Available valid evidence | Unavailable, invalid, or stale evidence |
| --- | --- | --- |
| `REQUIRED_FOR_DECISION` | Evaluate existing asset approval/report gate | Fail closed for that asset or report gate; preserve other scopes |
| `REQUIRED_FOR_SPECIFIC_RULE` | Evaluate the existing rule and measured signal | Rule unresolved; it cannot count as passed; cap only as that rule requires |
| `OPTIONAL_CONTEXT` | Display and apply an existing measured-signal rule if one actually consumes it | Display status; no absence-only eligibility cap |
| `DIAGNOSTIC_ONLY` | Audit/display | Audit/display; no financial effect |
| `NOT_APPLICABLE` / `UNSUPPORTED` | No invented result | State scope/stack limitation; no implicit global cap |

Observed adverse funding, OI change, liquidation imbalance, news quality, or price risk may still change an applicable existing rule. Optionality of **absence** does not neutralize a measured negative signal.

### Migration of existing reason codes and quality/confidence

Keep existing `alerts`, `limitations`, and `reason_codes` for old readers and historical comparison; add explicit metadata beside them. Do not mass-rename. Preserve genuine `insufficient_price_history`, `price_history_unavailable`, `stale_price_data`, real risk-plan infeasibility, and measured risk reasons. Target misleading behavior: `mixed_provider_data` and `source_mismatch_possible` become nonblocking absent demonstrated conflict; `ev_components_missing` stops capping valid EV; optional flow and unimplemented liquidations stop inheriting `*_unavailable` severity. `earnings_data_missing` remains an asset approval limitation for the clarified event-risk gate, with a more precise evidence status. `news_not_collected_confidence_limited` and similar labels must be audited against actual consuming rules rather than treated as policy because of their suffix. The report's `_has_confidence_limiting_limitation` and EV formatter must consume the explicit decision effect so rendering cannot recreate a removed cap.

Data completeness answers whether an applicable rule has required evidence. Data integrity answers whether that evidence is fresh, valid, compatible, and traceable. A financial signal answers what **observed** evidence implies. Decision confidence may reflect the legitimate rule-relevant evidence and quality policy, never arbitrary optional absence. Keep current public scores and thresholds unless the old generic coupling must be removed to meet these definitions; document every changed score in focused RED/GREEN evidence.

## Report-grade, operational integrity, discovery, and legacy boundaries

`primary_report_grade` remains an output of `evaluate_report_grades`; discovery may affect `overall_report_grade` and `discovery_coverage_grade`, not the primary minimum. Final review must read the primary grade and selected main's structured identity, artifact validity, blocking reasons, session, stale count, and required source status. `report_data_grade` must agree with that authority or explicitly report a conflict; it must not independently promote a diagnostic primary grade because coverage looks sufficient. Conversely, an overall diagnostic grade caused only by discovery must not block an otherwise valid primary tradeable. Keep discovery origin and no-promotion checks in main and final review.

For old reports without `evidence_trace_v1` or normalized context, preserve the existing selected main decision and real integrity gates, mark trace/context `legacy_unknown`, and avoid asserting that an optional gap was measured or that a required rule passed. Do not derive new criticality from old reason strings. A genuinely missing structured gate field remains unknown and is handled conservatively under the existing operational integrity contract. For a new artifact that declares v1, malformed or conflicting material trace is a source-consistency failure and cannot support stronger approval. The corrected new path must not retain known false generic caps for the sake of old artifact compatibility. Do not reprocess historical reports as if they had new metadata.

## Market-context and runtime transport decisions

Normalize observed market facts **once** at report emission, from the same in-memory benchmark candles and asset snapshots used by the report job. `advisor/cli.py` passes them into both report renderers; `advisor/report.py` emits a versioned market-context section, with explicit unavailable values when upstream has none. `advisor/analyst_review.py` parses that section from selected raw main (and checks a duplicated analyst/nightly copy for conflict), then renders Market Brief. Current prose metrics stay for compatibility, but BTC/ETH price and daily change do not depend on `_metrics_summary` labels. SPY/QQQ/SMH remain context, not watchlist/scored assets. Preserve already available stock/crypto regime labels and their source status. No `analyst_review.py` fetch or scoring call.

`scripts/fetch-latest-github-reports.ps1` presently copies the analyst input into the nightly input and retains raw main/close paths; its short `Main summary` is not a complete market-context copy. The final parser must therefore use the selected raw main for authority and the copied analyst section for boundary consistency, without assuming the short summary contains all observations. Its legacy `_classify_asset`, `_trade_block_summary`, and uncertainty prose currently infer restrictions from text; after v1 they may describe statuses but cannot transform optional flow/news absence into a main-integrity blocker or override a source decision. This is a presentation-semantic repair, not a new scoring branch.

Runtime metadata is independent of this market and decision trace. A missing runtime bundle can be investigated via producer trace path/status, uploaded reports tree, downloaded selected root, and sanitized manifest. The exact historical production cause remains unproven; this uncertainty cannot justify a workflow edit or a new financial gate. See [research.md](research.md) for the decision and rejected alternatives.

## Mandatory design review answers

1. **Central registry?** No global feed registry. The existing rule function owns a compact explicit dependency/effect declaration; share only the typed outcome format.
2. **Generic heuristics?** Replace decision and confidence effects with rule-scoped outcomes, retain old reason strings for diagnostic compatibility, and keep direct required-data checks. No pattern may silently grant financial authority.
3. **Earnings approval?** In stock classification immediately before promotion to `tradeable`, using verified event timing/clear-window evidence from snapshot status; never in primary report grade.
4. **Missing backtest statistics?** After adequate sample, mark each applicable win-rate/EV comparison unresolved if its consumed statistic is invalid or missing, and prevent approval through that rule.
5. **Valid EV with absent averages?** EV remains the direct sample mean. Omit average-only confidence/eligibility cap and misleading `limited/model_estimate` suffix; disclose absent averages as diagnostic.
6. **Provider compatibility?** Check capability-level identity, units, semantics, time and provenance; require a specific demonstrated conflict for an integrity cap. Mixing is diagnostic only.
7. **Context normalization?** Once in `advisor/report.py` at report emission, using existing `advisor/cli.py` in-memory benchmark/snapshot observations; carry the versioned section through existing artifacts.
8. **Structured final gating?** Extend `MainReviewContext` with semantic tri-state conflict and consume that plus primary grade and `main_blocks_operation`; no diagnostic substring checks or independent approval logic.
9. **Rule-capability trace?** Record a compact effect ledger at scoring/classification branches, serialize it with the source decision, and render it read-only in final review. Runtime trace is supplementary observability.
10. **Protected files/scope?** Risk/strategy/sizing, universe expansion, canonical/maturation, predictive calibration, broker/automation, V2 layout/transport, workflow YAML absent proof, frozen runtime catalog.
